## 结论（TL;DR）

- **爬梯 1–5 全 PASS**：attach（固件/eFuse MAC/power check 与 Linux GT 逐字节对拍）→
  scan 30+ BSSID（QiQiJia ch1 在表，ch1 修复随移植带入）→ WPA2 4-way（PTK/GTK=CCMP）→
  DHCP（192.168.0.10）→ ping 网关与 .18 各 20/20 0%。
- **iperf3 TCP 上行 10 分钟：PASS**——600 s 连续无停摆，1.89 Mbit/s（142,458,880 B，
  retransmits=0），测后 ping 网关 20/20 全通。**这是本板 RTOS 侧首次跑完 10 分钟 TCP 吞吐**
  （USB 线 M7+ 与 NetBSD KI-040 都在秒级~百秒级停摆）。
- **iperf3 TCP 下行：已收口（r3）**——r1 时数据流 4 s–6 min 后停；r2 取证
  定案块模式 CMD53 RX 数据损坏；r3 修复 dw_mmc 缓存维护后 **600 s 下行
  三轮冷启动全 PASS**（1.46/1.25/1.24 Mbit/s，测中测后 ping 20/20，见 r3 章）。
- **UDP 下行 30 s：PASS**（2.61 Mbit/s 均值，峰值 5.84，9.8 MB 零丢停）——
  r1 曾据此把停摆收敛到 lwIP TCP 层；r2/r3 证实真因在更底层的 dw_mmc
  RX 缓存维护（UDP 纯 RX 无 TX 交错所以幸免）。
- 修复链（本轮板测驱动）：①子双字 CMD53 对齐（dw_mmc datalen&3 拒绝）；
  ②**CTYPE 宽度枚举映射（根因）**——dwmmc 胶水把 fsl 枚举(0/1/2)直传给按字面比较的
  `dwc_mmc_set_card_bus_width`，4-bit 请求落进 1-bit 分支，host 1-bit 对 4-bit 卡，
  CMD52 通、CMD53 全 DCRC；③`wlan reg` 派发优先 rtw8189f（防 USB dongle 抢读）。

## iperf3 10 分钟稳定性（判据 5 细目）

**上行（板→server，600 s，TCP 单流）**
- cookie `iperf3-embedded.493023.8792`，params `time:600 len:4096`，server ack OK；
- 逐秒 interval 连续 0–600 全部打印，区间 1.11–2.52 Mbit/s，**平均 1.89 Mbit/s**；
- `iperf3 done: total 1.89 Mbits/sec (142458880 bytes in 600 sec)`，retransmits=0；
- 测后 `ping 192.168.0.1 20` = 20/20（11–104ms）；
- 期间无 fault/assert/spurious 风暴（一条 `irq: spurious` 属 GIC 历史基线）。
- 对照：USB 线 M7+ 同型测试 10 bulk 帧即停（open）；NetBSD KI-040 TCP 秒级契死——
  本结果首次证明 RTOS 侧 TCP 长流可行，且 SDIO 独立 TX 路径反证 USB 线停摆不在共享层。

**下行（server→板，600 s，TCP 单流，`-R`）**
- 复现 2 次（含换新 server 排除 server 侧）：数据流 4 s–6 min 后停止，
  interval 停打，`iperf3 stop` 可干净收尾（`iperf3 stop` 新命令生效）；
- 停摆后 `ping 192.168.0.1 5` = 5/5（11ms）——无线电链路存活，非 MAC 楔死；
- 楔死窗口 TXQ 取证（`wlan reg txq` 双读间隔 ~1s，逐字一致）：
  `CR=0x000206ff PBP=0x110 TRXFF_STATUS=0 HMETFR=0 RQPN=0xe5020c
   FIFOPAGE=0x00e5020c（hi16=0xe5=229 次累计 TXFF 溢出，窗口内不增长）
   TDECTRL=0x7c00f610 TXDMA_STATUS=0 RQPN_NPQ=0x202
   VOQ/VIQ/BEQ/BKQ/MGQ/HGQ=0x007f80ff（全队列同值静态）BCNQ=0x0fff00f6
   TXPAUSE=0x00`——固件未关阀、DMA 无错锁存、页计数不积累。
- **UDP 下行 30 s 对照：PASS**（2.61 Mbit/s 均值、峰值 5.84、9,804,412 B 零停摆）——
  下行停摆不在 SDIO/net80211 RX 批量路径，收敛到 lwIP TCP 接收窗口/ACK 路径。

**定位分层（定案）**
1. SDIO CMD52/CMD53（byte+block）、DMA、缓存纪律：**PASS**（76MB+ UDP/TCP RX、142MB TX）
2. net80211 收发 + RX 批量 + TX ack：**PASS**
3. TCP 上行长流：**PASS**
4. TCP 下行持续流：**已收口（r3）**——r1 判为 lwIP TCP 接收层（依据 UDP
   对照），r2/r3 重新定案：真因是 dw_mmc 适配层 RX 缓存维护/完成语义缺陷
   （UDP 无板内 TX 交错所以幸免，判别成立但指向偏了一层）。教训：UDP-pass
   能证明"批量 RX 基本可用"，不能证明"RX 在 TX 交错下无损坏"。

# M11 r2：TCP 下行停摆取证（2026-09-23，提交 07151d1 / net_80211 708be80）

镜像 sha256 `55dd57fa40c4b6bee28fc0f964f3d7aaa3d14d985cd918e466b528a3f1fd8472`。

**观测面**（常开保留）：`LWIP_STATS=1 + stats_display()` + shell `lwstats`；
lwIP 桥四计数器 + `wlan stats`（ic_stats + 桥）；`wlan sdreg`（SDIO-local
HISR/HIMR/RX0_REQ_LEN/FREE_TXPG）。pktmon（Windows 宿主，WSL interop 驱动）
0-drop 抓包两份留档：`D:\pktmon-stall\stall.pcapng`（停摆轮，pipeline drop 7030）、
`D:\pktmon-stall\paced.pcapng`（限速对照，0 drop）。

**取证链（定案：块模式 CMD53 RX 数据损坏，非 lwIP 窗口）**

1. 0-drop pcap：服务器持续发送并 RTO 重传，板端 ACK 序号全程停在 1、约 19 s 后
   服务器 RST 放弃——板子不是"收到了不 ACK"，而是**段根本没以完好形态到达 TCP**。
2. 尺寸判别：`ping -l 1400` 0/4 全灭 vs `-l 32` 4/4 全过——大帧（块模式
   CMD53，>512B）路径专属，小帧（非块模式）无恙。这就是 beacon/ARP/ICMP/
   关联一直活着的原因。
3. 大帧确实到达驱动：`ucast_rx` 随服务器重传爬升、`rx_errors` 同步爬升——
   记录在驱动侧被判坏丢弃（desc 校验/CRC），偶发漏到 lwIP 的也是短帧
   （IP lenerr 累计 1405+）。
4. 桥三层计数器全零（gated/pbuf_fail/take_fail/input_fail）——net80211→lwIP
   之间无丢弃，排除桥层。
5. `TCP_WND` 32*MSS=46,720 超芯片 16KB RX FIFO（`RX_DMA_SIZE_8188F=0x4000`）
   属叠加风险，裁到 4*MSS（SND_BUF 保持 32*MSS，USB 线上行修复不受影响），
   但**单独不能止停摆**——总线层才是主因（r3 证实）。
6. UDP 30s 2.61 Mbit/s PASS 与 TCP 停摆并存 → 损坏与**板内 TX 交错**相关
   （TCP 每 ~2 MSS 一个 ACK 出站；UDP 纯 RX）。

预下载队列几何修复（PBP/RX_DRVINFO_SZ/TDECTRL/TRXFF_BNDY 在 8051 复位期写入，
对齐 rtl8189fs `_InitTransferPageSize` 次序）随本轮落地并镜像 NetBSD
（netbsd-11 `111525e242df`）。

# M11 r3：停摆根因修复与三轮回归收口（2026-09-23，提交 36fc3ec）

**根因（代码级实证，对拍 NetBSD `dwc_mmc.c` 同 IP 驱动）——我们自己 dw_mmc
适配层的三个缺陷：**

1. **RX 缓冲 DMA 前无 invalidate**（`drivers/dwc_mmc.c` prepare_dma 只在写方向
   flush）：stage 缓冲上的脏行若在 DMA 窗口内被普通容量驱逐写回，覆盖正在
   接收的数据。
2. **DTO 即成功，不等 IDMAC 收尾**：DTO 只表示控制器吃完全线数据，IDMAC
   FIFO→RAM 尾部还在途；原实现此刻就 invalidate+memcpy，记录尾部可读到
   上一条记录的旧数据。NetBSD 的 ISR 等的正是 `IDST_RECEIVE_INT`（IDSTS.RI）。
3. **stage memcpy 在 fsl card->lock 之外**——审计后证实**已被覆盖**：rtw8189f
   work 线程持有 port serializer 横跨 TX 帧与 RX drain（`if_rtw8189f.c`
   work loop），所有总线访问单线程串行，无需新锁（契约已写入
   wlan_sdio_claim.c 头注释）。

**修复**（`drivers/dwc_mmc.c` + `drivers/dwc_mmc_regs.h`）：
- 读方向在开门铃前 `board_dcache_invalidate(buf, datalen)`（对齐 NetBSD
  PREREAD 语义）；
- arm 前清 IDSTS 并**编程 IDINTEN**（RI|TI|NI|AI|FBE|DU|CES）——板验当场
  定位：**本 IP 上 IDSTS 状态位不使能对应 IDINTEN 就不置位**（首版修复只
  读 RI 得到恒 0x0、全部数据命令失败的洪泛；NetBSD 写 IDIE、Linux
  `dw_mci_idmac_init` 同样先编程 IDINTEN，poll 模式此前从未使能过）；
- wait_data_over：DTO 后轮询 IDSTS.RI（含 IDMAC 错位检查、超时预算复用），
  RI 后清 IDSTS 再 invalidate（兼防消费核与预 invalidate 核不同）。
