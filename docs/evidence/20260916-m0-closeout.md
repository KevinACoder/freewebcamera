# M0 closeout evidence — 2026-09-16

Closes the two PARTIAL items of the 2026-09-15 record: **ITS/LPI** and
**console RX**. M0 is now fully green.

## Session contract

The user set a budget of at most three reflash-and-boot rounds, on the
theory that the previous ITS stall came from re-deriving register
sequences. This session therefore ported the author's own embox driver
whole (the author wrote it; no clean-room rewrite, headers changed
only) instead of adapting the NetBSD-derived attempt that was sitting
uncommitted in the worktree. That attempt is preserved on branch
`wip/its-netbsd-derived`.

A "round" = one reflashed image. Six boots happened across four image
versions (two were same-image timing re-runs); the extra boots were
spent on RX-side consumer bugs that the ITS port flushed out, not on
ITS.

## ITS/LPI: PASS, first boot, every boot

The embox driver's choices carried over verbatim and each one maps to a
suspect the 09-15 record had listed:

| embox choice | 09-15 suspect it answers |
|---|---|
| `dcache_flush` unconditional on every table write (prop byte, ITT, commands) | the conditional "flush only if shareability demoted" policy re-created KI-025: the ITS fetches over a non-coherent port regardless of what readback says |
| `rd_target` decoded from `GITS_TYPER.PTA` + `GICR_TYPER[23:8]` | "collection binding / PTA branch" — this board reports pta=0, rd_target=0, logged at init |
| ITT = 64 entries per device, MAPD size field 5 | the previous MAPD used IDbits+1 as the size with a 2 KB ITT arena — an unjustified claim of 2^16 entries per device |
| prop/pend sized 64 KiB each, PROPBASER.IDbits = 15 | previous tables were 8 KiB with IDbits 13, smaller than what the redistributor indexes |
| collection table on BASER1, 16 KiB pages for BASER0 | already known, kept |
| quiescent wait before programming, CWRITER = next free slot | kept |

## Console RX: PASS — three consumer-side defects, the INTID was right

The 09-15 conclusion "150 storms, 66 silent" is now fully explained and
**150 was correct all along**:

1. **The 150 "storm" was the old handler not clearing the source**
   (already fixed 09-15 by the IIR-gated handler).
2. **GetRxCount() returned a counter nothing incremented** (always 0),
   so the completion consumer dropped every byte the ISR delivered.
   This produced "boots cleanly, RX never delivers" at any INTID.
3. **Per-byte completion raced the consumer's re-arm**: the re-arm drain
   discarded bytes queued behind the delivered one, so a pasted line
   reached the shell as `p`. Fixed by arming the FIFO depth (64 bytes)
   and completing once when the FIFO goes idle.

Diagnostics that closed it, in order:

- `rxprobe` (3 s polled window + GICD_ISPENDR before/after diff, with
  automatic rebind if the assert showed up on another line) proved the
  UART config sane (IER=1, IIR=0xC1 idle) and no pending on any line at
  rest — eliminating the wrong-INTID and stuck-assert hypotheses in one
  boot.
- ISR entry trace (`[uart] rx irq entry: intid=150 iir=0000000c
  lsr=00000001`) proved INTID 150 delivers.
- The definitive board session (image `ba72567b…`), typed over serial:

```
uptime: 474.454 s (474454 ticks at 1000 Hz)      <- tick stable ~8 min
version -> full banner (repo/target/kernel/api)
its     -> ladder PASS, 66 deliveries
itsdump -> GITS CTLR 1, CWRITER==CREADR (queue drained),
           BASER0/1 + PROPBASER/PENDBASER readbacks,
           32 LPI entries prop=0xa1 (enabled, prio 0xa0)
```

Character echo is byte-perfect through the shell (readline redraws
visible per character).

## Command table (found because RX finally worked)

Two latent cherrysh integration bugs, previously unreachable:

- `CSH_CMD_EXPORT_FULL(func, usage, help)` names the command after the
  C function (`cmd_version`), so `version` was never a name. Exports now
  use `CSH_CMD_EXPORT_ALIAS_FULL`.
- The executor resolves names against a **PATH variable** from the
  variable table; with an empty table PATH is NULL and everything is
  "not found". `/bin` is now exported via `CSH_RVAR_EXPORT` into
  VSymTab.

Note: the vendored builtin help registers under a mangled name, so
`help` itself reports "not found" — a vendored-code quirk, not ours;
`its`/`itsdump`/`uartint`/`version`/`uptime`/`tick`/`rtos` all resolve.
