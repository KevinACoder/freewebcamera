## Root cause of the bring-up failure

`port/board/gicv3.c` defined the priority register as

```c
#define GICD_IPRIORITYR(n) (0x0400 + 4 * (n))
```

but every accessor uses `reg_wr8` / `reg_rd8`: the register is **one byte per
INTID** at `0x400 + id`, with no stride. With the 4x stride the loop that seeds
default SPI priorities walked `0x480` upward instead of `0x420` upward, and by
INTID ~256 it was writing past the end of the priority bank (which ends at
`0x7ff`) into reserved space at `0x800`+.

On this SoC a write into that hole does not fault cleanly - **the SoC resets**.
That is why the failure looked like a GIC hang, and why the death point moved
between builds and was so hard to pin down.

Confirmed by a heartbeat loop placed immediately *after* `IRQ_Initialize()`:
it printed ~40 consecutive 1 Hz beats (`boot-200022-5d22`), so distributor,
redistributor and CPU interface all complete.

## Four bugs found and fixed this session

1. **`GICD_IPRIORITYR` 4x stride on a byte-granular register** - the root cause
   above.
2. **Device mappings were shareable.** `mmu.c` used one descriptor helper that
   OR'd `SH_INNER` into every entry, including Device entries. Device memory is
   Non-shareable and a shareable Device mapping is UNPREDICTABLE; the symptom
   is a stale peripheral status read, which mimics a dead peripheral. Split
   into `device_block_desc()`.
3. **`make` had no default goal.** The first explicit target was the ELF rule,
   so a bare `make` built no image and left a stale `freertos.bin` on the TFTP
   root - a failed rebuild presenting as a boot failure. Fixed with
   `.DEFAULT_GOAL := all`.
4. **Tick priority and trigger mode.** `tick.c` requested
   `IRQ_MODE_TRIG_EDGE_RISING` for a level-sensitive PPI, and used raw `0xf0`
   where the port asserts `portLOWEST_USABLE_INTERRUPT_PRIORITY << 4` = `0xe0`.
   Also removed `configKERNEL_INTERRUPT_PRIORITY`, which this AArch64 SRE port
   never reads.

Earlier sessions had already fixed: entry point not at the load address, and a
page-table walk one level short.

## Correction to a prior assumption

The plan asserted libfreebsd's carrier "does not work" and must not be used as
a reference. **That is wrong, and this board says so.** The archived image
`_baseline/pre-m0-freertos.bin.bak` (sha256
`b16c254f8f53190eeeade327bdd2beb6352379a1b4caeb515d7a9bac8cf27b83`) boots to:

```
libfreebsd freertos/rk3568 carrier
cntfrq=24000000
FRT/BOARD SWITCH OK (a=3 b=5)
FRT/BOARD SPI SOFTTRIG OK
FRT/BOARD ANCHORS OK
FRT/BOARD TICK OK (ticks=1004)

FRT/PANIC: its lpi silent
```

It reaches task switching, the tick, and a software-triggered SPI; it fails
only at ITS/LPI. Its source is not present anywhere in this workspace
(searched), so it can be run but not read.

## Open blocker

Acceptance build sha256
`37a02d55e5be6543bc280f26430a0e1c9749e24408a7273b8dd5edc2234e4ba4`
still stops printing immediately after the banner, reproducibly.

The shape of the failure points at the console transmit path, not the GIC: the
banner is ~45 bytes and fits entirely in the 64-byte UART FIFO, so its `Send`
never has to wait, while the *next* `Send` (`cntfrq=`) is the first that must
poll `LSR.THR_EMPTY`. An unbounded poll that never clears hangs exactly there,
leaving a clean complete line as the last output.

Against that: the heartbeat loop placed after `IRQ_Initialize()` pushed
hundreds of bytes through the same `Send` path for 40 s. So a permanent stall
is not certain, and the next step is to capture the raw byte stream rather than
reason from the line-assembling reader.

## Hardware facts reconfirmed

- Console UART2 `0xfe660000`: `GIC_SPI 118` → **INTID 150**. Three independent
  device trees agree (lab U-Boot `arch/arm/dts/rk3568.dtsi:2258`, vendor kernel
  `rk356x.dtsi:3011`, mainline `rk356x-base.dtsi:1461`; uart1..uart9 = SPI
  117..125). The lab's FreeBSD logs report `irq 66` for the same base - **still
  unexplained, resolve before relying on 150.**
- GICD `0xfd400000`, GICR `0xfd460000`, ITS `0xfd440000`, all confirmed against
  `rk356x-base.dtsi`.

## Reading the serial capture (two traps that cost real time)

1. The reader assembles **complete lines**. A stream without newline is
   invisible even though the bytes arrive: the heartbeat printing `hb ` looked
   like a hang, and printing `hb\n` was visible at once. "No output" can mean
   "no complete line".
2. The reader **drops bytes under load**. Flooding the console loses characters
   and can cut a line mid-word, mimicking a crash at that point. Space
   bring-up output out.
