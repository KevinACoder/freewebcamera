Every call in the acceptance app goes through CMSIS-RTOS2 (`osKernelInitialize`,

### CMSIS-RTOS2 primitive sweep

Each check is a round trip with an observable result, not a call assumed to have
worked. The sweep is why `osThreadFlagsSet` was caught returning 0 instead of
the post-set flag value that CMSIS specifies - a contract violation that no
amount of "the call did not crash" would have revealed.

Covered: semaphore release/acquire/count, queue put/get with **order**
verified and element size read back, mutex acquire/owner/release, event flags
set/read, one-shot timer whose callback is *waited for* in the timer task
(a different context on purpose), memory-pool alloc/write/count/free, and
thread flags set/get/selective-clear with the pre-clear value checked.

Failures are counted, and the "CMSIS RTOS2 OK" line only prints when the count
is zero - an earlier revision printed it unconditionally, which would have
reported success immediately below a failure line.

### Kernel seam (K4)

`make k4` links `app/` and `drivers/` against a **null CMSIS-RTOS2
implementation** (`port/adapters/stub/cmsis_os2_stub.c`) with no FreeRTOS
sources, no kernel include paths and no port glue. It builds. That is the M0
modularity claim tested rather than asserted: nothing above the adapter depends
on FreeRTOS, so the kernel is genuinely replaceable.

`k4` is part of `make gates`, so if `app/` or `drivers/` ever picks up a kernel
dependency it fails there rather than at some later kernel swap.

`vectors.S` is deliberately excluded from the K4 link: it branches to the
FreeRTOS port's handlers, so it belongs to the kernel side of the seam. What is
under test is that the layers above link with no kernel, not that the kernel's
own glue is absent.


## Root causes found (four, all silent-failure class)

### 1. `GICD_IPRIORITYR` — 4x stride on a byte-granular register

Defined as `0x0400 + 4 * n`, but every accessor performs a one-byte access and
the register is one byte per INTID at `0x400 + id`. The loop seeding SPI
priorities walked off the end of the bank (which ends at `0x7ff`) into reserved
space at `0x800`+, and a write there **resets this SoC**.

This is what produced the long hunt: the board did not hang, it rebooted, so
the "last line printed" moved between builds and never marked the real fault.

### 2. `GICR_*_0` offsets added to an already-offset base

The redistributor is two 64KiB frames: RD_base at +0 and SGI_base at +0x10000.
The code held `gicr_base = GICR + 0x10000` **and** added offsets that already
contained `0x10000`, so every SGI/PPI access landed at RD + 0x20100 instead of
RD + 0x10100.

Consequence, and it is the quietest failure of the four: the timer raised its
interrupt and set `GICR_ISPENDR0` bit 27 correctly, but the **enable** bit was
written into unused space. INTID 27 was never enabled, so no tick ever reached
the CPU. The scheduler started, ran the first task, and then every `osDelay()`
blocked forever - which looks exactly like a hung scheduler rather than a
mis-addressed register. Found by reading the state from inside a task:
`CNTV_CTL=0x05` (running), `ISENABLER0 bit27 = 0`, `ISPENDR0 bit27 = 1`.

All offsets in `gicv3.c` are now relative to `gicr_base` = RD_base, with no
second addition anywhere.

### 3. `ICC_IGRPEN1_EL1` was deliberately not written

The file asserted that a non-secure write to it resets the board. That was
wrong: the board-proven GICv3 path for this SoC writes it. It is now written
(read, set bit 0, write) when not already enabled.

### 4. `GICR_IGRPMODR0` not cleared when enabling a PPI

Setting `IGROUPR0` alone is not enough: `IGROUPR0=1` with `IGRPMODR0=1` is
Group 1 **Secure**, which a non-secure handler never receives. Reads back
"correct" while delivering nothing. `IRQ_Enable` now clears `IGRPMODR0` for the
requested line only, as it already did for `IGROUPR0`.

## Also fixed

- **UART register access was shifted twice.** The constants are already byte
  offsets (the part is `reg-shift=2`, `reg-io-width=4`, so LSR index 5 is at
  0x14), but the accessors shifted again. Only THR (offset 0) was unaffected -
  which is the sole reason the console appeared to work at all: transmission
  functioned because U-Boot had already programmed the UART, and our own
  LCR/IER/MCR writes were silently landing on the wrong registers. The symptom
  was a console that printed a banner and then stopped dead, because the first
  write that had to poll for FIFO room read LSR from the wrong address.
- **`make` had no default goal**, so a bare `make` built no image and left a
  stale `freertos.bin` on the TFTP root: a failed rebuild presenting as a boot
  failure.
- **Device mappings were shareable.** `mmu.c` OR'd `SH_INNER` into every
  descriptor including Device entries. Device memory is Non-shareable and a
  shareable Device mapping is UNPREDICTABLE; the symptom is a stale peripheral
  status read.
- **Boot-time cache hygiene**: drain the loader's dirty lines over our own
  image before enabling caches, so a stale write-back cannot land on the page
  tables or stack.
- **Tick priority and trigger mode**: `tick.c` asked for edge-triggered mode on
  a level-sensitive PPI, and used raw `0xf0` where the port asserts
  `portLOWEST_USABLE_INTERRUPT_PRIORITY << 4` (= `0xe0`). Removed
  `configKERNEL_INTERRUPT_PRIORITY`, which this AArch64 SRE port never reads.
- **Gates**: `cleanroom-scan.sh` matched its own pattern list and so failed
  every run; `check-deps.sh` checked only `app/` and `drivers/`. Now the scan
  excludes itself and generated dirs, and the dependency check also covers
  `port/board/`, matches `<angle>` includes, and flags `FreeRTOSConfig.h`.

## Correction to a prior assumption

The plan asserted libfreebsd's carrier "does not work" and must not be used as
a reference. **That is wrong, and this board says so.** The archived image
`_baseline/pre-m0-freertos.bin.bak` (sha256
`b16c254f8f53190eeeade327bdd2beb6352379a1b4caeb515d7a9bac8cf27b83`) boots to
`SWITCH OK` / `SPI SOFTTRIG OK` / `TICK OK` and fails only at ITS/LPI. Its
source is not present anywhere in this workspace (searched), so it can be run
but not read.

## Hardware facts

- Console UART2 `0xfe660000`: `GIC_SPI 118` → **INTID 150**. Three independent

  `rk356x.dtsi:3011`, mainline `rk356x-base.dtsi:1461`; uart1..uart9 = SPI
  117..125). The lab's FreeBSD logs report `irq 66` for the same base -
  **still unexplained; resolve before relying on 150 for RX.**
- GICD `0xfd400000`, GICR `0xfd460000`, ITS `0xfd440000` (confirmed against
  `rk356x-base.dtsi`). Measured `GICD_CTLR = 0x12` (DS=1, ARE_NS set),
  `GICD_TYPER = 0x007b040a`.
- No watchdog: a 6 s idle loop after the banner completes and keeps running.

## Reading the serial capture (two traps that cost real time)

1. The reader assembles **complete lines**. A stream without newline is
   invisible even though the bytes arrive - a heartbeat printing `hb ` looked
   like a hang; the same heartbeat printing `hb\n` was visible immediately.
   "No output" can mean "no complete line".
2. The reader **drops bytes under load**. Flooding the console loses
   characters and can cut a line mid-word, mimicking a crash at that point.
   Space bring-up output out. (Visible in the transcripts above, where
   high-rate heartbeat markers appear interleaved into our own strings.)
