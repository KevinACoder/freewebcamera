# M0 bring-up evidence — 2026-09-15

## Status: PARTIAL PASS

Boot path works up to the console banner; the system then stops inside GIC
bring-up. **Not** a full M0 pass — see "What is not yet proven" below.

## What was verified on the board (today, real hardware)

Command sequence driven by the oslab `freertos` profile (cold power-cycle, per
KI-001):

```
setenv autoload no

```

Serial output observed after `go`:


### What that proves

| Fact | Evidence |
|---|---|
| U-Boot loads and jumps to the image | `Bytes transferred = 46352`, `## Starting application` |
| `_start` is at the load address and executes | banner printed, which only happens after `board_main` |
| EL2→EL1 drop and `CurrentEL` decoding work | code past the EL branches runs |
| Identity-mapped MMU with caches on works | C code runs; the banner is printed via the MMU-mapped device frame |
| CMSIS `ARM_DRIVER_USART` console works | `Send()` output, polled, 115200 8N1 |
| `CNTFRQ_EL0` readable from EL1 | `cntfrq=24000000` |

## Two real bugs found and fixed by this run

### 1. Entry point was not at the load address

The link script placed `.vectors` first, so `go 0xa000000` began executing the
**exception vector table**. Its first entry branches to the fault handler,
which parks before the console exists — the image loaded, ran, and printed
nothing.

Fixed by putting `KEEP(*(.text.boot))` first. The vector tables are located by
pointer (`boot_vectors`, `_freertos_vector_table`), so they do not need
offset 0.

Verified: `nm` shows `_start` at `0x0a000000`.

### 2. Page-table walk was one level short

`T0SZ=16` (48-bit VA, 4KiB granule) means a **four**-level walk starting at L0,
where only table descriptors are legal. The code put 1GiB *block* descriptors
in what was actually the L0 table and filled L1 with 2MiB blocks. The
descriptor was invalid, so the first fetch after enabling the MMU took a
translation fault into the parking handler — again silent.

Fixed by adding a real L0 table and pointing `TTBR0_EL1` at it.

This is what moved the board from "no output at all" to the banner.

## Known remaining issue (why this is not a full pass)

Output stops after `cntfrq=24000000`, i.e. inside interrupt-controller
bring-up. Progress markers (`[gicv3] dist` / `redist` / `cpuiface` / `ready`)
were added but the run that would show them had not completed when this record
was written. The next board session must:

1. re-run and capture which marker is last;
2. fix that step;
3. then look for `SWITCH OK` / `TICK OK` / `SPI SOFTTRIG OK` / `M0 ANCHORS DONE`.

A second real bug was fixed speculatively in the same commit and is **not yet
verified**: `board_gicv3_init` cleared `GICD_CTLR` with a plain store, which
drops ARE (firmware boots with DS=1 and ARE set). It now uses a read-modify-
write of only the `EnableGrp1NS` bit. This matches the board fact recorded in
the file header and in the workspace DESIGN doc, but the fix has not been
observed working.
