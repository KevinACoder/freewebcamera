# M0 bring-up evidence — 2026-09-15

## ITS/LPI: PARTIAL — bring-up works, delivery not yet achieved

The driver exists (`port/board/gicv3_its.c`, `gicv3_its.h`) and the following
are **demonstrated working on hardware**, because the ladder reaches rung 2:

- ITS command queue configured and accepted (`GITS_CBASER` write survives
  readback, shareability accepted rather than silently refused)
- Device table (16-bit DeviceID → 65536 entries, 512KiB, 16KiB pages) and
  collection table located by **reading each `GITS_BASERn`'s type field** rather
  than assuming slot 0/1 - this board requires the collection table in BASER1
  and silently discards a write to any other slot
- `MAPD` (bind a device's ITT) and `MAPTI` (bind event → LPI) both execute and
  the queue drains, so command submission, `INV` and `SYNC` are all sound
- The redistributor accepts `GICR_PROPBASER` / `GICR_PENDBASER` and
  `GICR_CTLR.EnableLPIs`
- The property table is written with the cache flush that this path cannot work
  without

**Not yet achieved:** rung 2, a single LPI actually reaching its handler after
`ITS_CMD_INT`. The selftest reports `[its] selftest rung2: single LPI not
delivered` and stops there, so rungs 3 and 4 have not been exercised.

Fixed along the way, both found by the ladder:

1. **`GITS_CTLR.Enable` was written last.** The ITS does not process its
   command queue while disabled, so `MAPC` sat unread and the drain loop timed
   out - which presents as "the ITS is broken" rather than "it was never
   switched on". Enabled before any command now.
2. **The CPU cannot ring the doorbell.** A store to `GITS_TRANSLATER` carries no
   Requester ID, so the ITS cannot attribute it to a DeviceID and drops it -
   even with a perfectly correct mapping. Injection must use the ITS's own INT
   command (`0x03`). This is why rung 2 must be driven by `ITS_CMD_INT`.

Remaining suspects for rung 2, in the order worth testing:

- **Device ID / `ICID` vs collection.** `MAPC` was issued with collection id 0
  and `MAPTI` with the same; if the collection table entry does not actually
  bind to this redistributor, translation succeeds and delivery goes nowhere.
- **ITT entry size.** `GITS_TYPER` reports an ITT entry size that this file
  currently assumes rather than decodes. An ITT laid out with the wrong stride
  maps the right event to the wrong slot, which is invisible.
- **Redistributor LPI table addressing.** `GICR_PROPBASER.IDbits` is written as
  a constant (16) because `GICD_TYPER` is unreliable here; if the real width
  differs, the ITS and the redistributor disagree about the table layout.
- **`GITS_TYPER.PTA`.** `MAPC`'s RDbase field means "physical address" only when
  PTA is set. This file branches on it, but a wrong branch here is silent.

What the lab's own board-proven ITS test does differently is worth noting for
the next attempt: it validates the simple case *before* adding anything else,
and it decodes `GITS_TYPER` rather than assuming. `ITSTestSimple` in
`os/standalone/example/peripherals/gicv3/master/src/lpi_example.c` is the
reference.

This is the one M0 gate item not met. It is recorded as **PARTIAL**, not passed.

### CMSIS-RTOS2 primitive sweep

Each check is a round trip with an observable result, not a call assumed to have
worked. The sweep is why `osThreadFlagsSet` was caught returning 0 instead of
the post-set flag value that CMSIS specifies - a contract violation that no
amount of "the call did not crash" would have revealed.

Covered: semaphore release/acquire/count, queue put/get with **order**
verified and element size read back, mutex acquire/owner/release, event flags
set/read, one-shot timer whose callback is *waited for* in the timer task
(a different context on purpose), memory-pool alloc/write/count/free, and
thread flags set/get/selective-clear with the pre-clear value checked.

Failures are counted, and the "CMSIS RTOS2 OK" line only prints when the count
is zero - an earlier revision printed it unconditionally, which would have
reported success immediately below a failure line.

### Kernel seam (K4)

`make k4` links `app/` and `drivers/` against a **null CMSIS-RTOS2
implementation** (`port/adapters/stub/cmsis_os2_stub.c`) with no FreeRTOS
sources, no kernel include paths and no port glue. It builds. That is the M0
modularity claim tested rather than asserted: nothing above the adapter depends
on FreeRTOS, so the kernel is genuinely replaceable.

`k4` is part of `make gates`, so if `app/` or `drivers/` ever picks up a kernel
dependency it fails there rather than at some later kernel swap.

`vectors.S` is deliberately excluded from the K4 link: it branches to the
FreeRTOS port's handlers, so it belongs to the kernel side of the seam. What is
under test is that the layers above link with no kernel, not that the kernel's
own glue is absent.


## Root causes found (four, all silent-failure class)

### 1. `GICD_IPRIORITYR` — 4x stride on a byte-granular register

Defined as `0x0400 + 4 * n`, but every accessor performs a one-byte access and
the register is one byte per INTID at `0x400 + id`. The loop seeding SPI
priorities walked off the end of the bank (which ends at `0x7ff`) into reserved
space at `0x800`+, and a write there **resets this SoC**.

This is what produced the long hunt: the board did not hang, it rebooted, so
the "last line printed" moved between builds and never marked the real fault.

### 2. `GICR_*_0` offsets added to an already-offset base

The redistributor is two 64KiB frames: RD_base at +0 and SGI_base at +0x10000.
The code held `gicr_base = GICR + 0x10000` **and** added offsets that already
contained `0x10000`, so every SGI/PPI access landed at RD + 0x20100 instead of
RD + 0x10100.

Consequence, and it is the quietest failure of the four: the timer raised its
interrupt and set `GICR_ISPENDR0` bit 27 correctly, but the **enable** bit was
written into unused space. INTID 27 was never enabled, so no tick ever reached
the CPU. The scheduler started, ran the first task, and then every `osDelay()`
blocked forever - which looks exactly like a hung scheduler rather than a
mis-addressed register. Found by reading the state from inside a task:
`CNTV_CTL=0x05` (running), `ISENABLER0 bit27 = 0`, `ISPENDR0 bit27 = 1`.

All offsets in `gicv3.c` are now relative to `gicr_base` = RD_base, with no
second addition anywhere.

### 3. `ICC_IGRPEN1_EL1` was deliberately not written

The file asserted that a non-secure write to it resets the board. That was
wrong: the board-proven GICv3 path for this SoC writes it. It is now written
(read, set bit 0, write) when not already enabled.

### 4. `GICR_IGRPMODR0` not cleared when enabling a PPI

Setting `IGROUPR0` alone is not enough: `IGROUPR0=1` with `IGRPMODR0=1` is
Group 1 **Secure**, which a non-secure handler never receives. Reads back
"correct" while delivering nothing. `IRQ_Enable` now clears `IGRPMODR0` for the
requested line only, as it already did for `IGROUPR0`.

## Also fixed

- **UART register access was shifted twice.** The constants are already byte
  offsets (the part is `reg-shift=2`, `reg-io-width=4`, so LSR index 5 is at
  0x14), but the accessors shifted again. Only THR (offset 0) was unaffected -
  which is the sole reason the console appeared to work at all: transmission
  functioned because U-Boot had already programmed the UART, and our own
  LCR/IER/MCR writes were silently landing on the wrong registers. The symptom
  was a console that printed a banner and then stopped dead, because the first
  write that had to poll for FIFO room read LSR from the wrong address.
- **`make` had no default goal**, so a bare `make` built no image and left a
  stale `freertos.bin` on the TFTP root: a failed rebuild presenting as a boot
  failure.
- **Device mappings were shareable.** `mmu.c` OR'd `SH_INNER` into every
  descriptor including Device entries. Device memory is Non-shareable and a
  shareable Device mapping is UNPREDICTABLE; the symptom is a stale peripheral
  status read.
- **Boot-time cache hygiene**: drain the loader's dirty lines over our own
  image before enabling caches, so a stale write-back cannot land on the page
  tables or stack.
- **Tick priority and trigger mode**: `tick.c` asked for edge-triggered mode on
  a level-sensitive PPI, and used raw `0xf0` where the port asserts
  `portLOWEST_USABLE_INTERRUPT_PRIORITY << 4` (= `0xe0`). Removed
  `configKERNEL_INTERRUPT_PRIORITY`, which this AArch64 SRE port never reads.
- **Gates**: `cleanroom-scan.sh` matched its own pattern list and so failed
  every run; `check-deps.sh` checked only `app/` and `drivers/`. Now the scan
  excludes itself and generated dirs, and the dependency check also covers
  `port/board/`, matches `<angle>` includes, and flags `FreeRTOSConfig.h`.

## Reading the serial capture (two traps that cost real time)

1. The reader assembles **complete lines**. A stream without newline is
   invisible even though the bytes arrive - a heartbeat printing `hb ` looked
   like a hang; the same heartbeat printing `hb\n` was visible immediately.
   "No output" can mean "no complete line".
2. The reader **drops bytes under load**. Flooding the console loses
   characters and can cut a line mid-word, mimicking a crash at that point.
   Space bring-up output out. (Visible in the transcripts above, where
   high-rate heartbeat markers appear interleaved into our own strings.)

## CherrySH: PARTIAL — shell starts, console RX unresolved

The shell is integrated and its task starts (`SHELL READY` printed on hardware,
after which the acceptance anchors run normally):

- CherrySH + CherryRL + CherryRB vendored sources build and link
- `csh_config.h` supplied as a shadow config in `port/adapters/cherrysh/`
  (never inside `third-party/`), with `CONFIG_CSH_NOBLOCK=1` +
  `CONFIG_CSH_LNBUFF_STATIC=1` so the REPL never blocks in `sget`
- The shell task blocks on an `osThreadFlagsWait` and is woken by the console
  interrupt, rather than spinning in `chry_readline_waitkey()` - a spinning
  shell would silently starve every lower-priority task
- Five commands registered through `CSH_CMD_EXPORT_FULL`, including `its` which
  runs the ITS ladder from the shell
- A freestanding libc shim (`port/board/minilibc.c`) supplies `strnlen`,
  `memchr`, `strcmp`, `strncmp`, `strncpy`, `strchr`, `atoi`, `snprintf` and
  `vsnprintf` for the shell; `memops.c` alone was not enough
- `osThreadFlagsSetFromISR` added as a documented project extension in
  `port/adapters/cmsis_rtos2/cmsis_os2_ext.h`, since CMSIS-RTOS2 has no ISR-safe
  flag setter and the vendored header must stay byte-identical (gate K7)

**Not achieved:** console receive. A byte typed at the console does not reach
the shell. Two candidate INTIDs were tested on hardware, and the results are the
useful part of this record:

| INTID | Result |
|---|---|
| 66 (lab FreeBSD logs, `irq 66` for this base) | Boots cleanly through every anchor; RX never delivers a byte |
| 150 (GIC_SPI 118 per three device trees) | Immediate **interrupt storm** - the line re-asserts continuously and the system wedges before printing anything else |

Draining the UART's RX FIFO does not clear the INTID 150 storm, which rules out
"a stray byte in the FIFO" as the cause. That leaves two explanations, and the
ISR itself can distinguish them: either that line belongs to a **different
asserting peripheral** on this SoC, or the UART is asserting for a reason that
reading RBR does not clear (a line-status condition - overrun/framing/break - is
the usual suspect).

**Next step is therefore specific and small:** have the ISR read `IIR` and
`LSR`, and print the interrupt identification code and the line status. `IIR`
says *why* the part is asserting; `LSR` says whether it is an error rather than
data. That one change distinguishes all the remaining possibilities, instead of
guessing between two INTIDs.

The configuration ships with INTID **66** because a silent console is
recoverable and an interrupt storm is not.

A related ordering bug was found and fixed on the way, and is worth recording
because it produced the same symptom as a wrong INTID: the console interrupt
must not be enabled until the receive state exists and the FIFO has been
drained, or the handler runs against `rx_active == 0`, consumes nothing, and the
level-triggered line stays asserted forever. `usart_rx_start()` now does
handler -> priority -> state -> drain -> IER -> enable, in that order.
